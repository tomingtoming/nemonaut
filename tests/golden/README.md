# 基準データ

物理の結果を固定するための記録です。固定の初期状態と、1/120秒ごとの操作列を再生し、記録済みの結果と許容幅の中で一致することを確かめます。

## 基準再生（js-v1.json、js-v2.json、js-v3.json）

| ファイル | ケース | 記録に使った物理 |
|---|---|---|
| `js-v1.json` | 8件：ローバーの走行・旋回・制動、小型機と大型機の接地、軌道上の漂流、段の分離と資源、空のタンクと満タンのタンクの衝突、翼の過荷重 | 以前のJavaScript版のソルバー（npmのRapier 0.21.0） |
| `js-v2.json` | 2件：衝突時に壊れる部品が、接触インパルスの大きさの順で決まること | 同上 |
| `js-v3.json` | 4件：機体どうしの衝突（軌道上での低速の接触、高速の衝突、衝突で生じた破片どうしの衝突）と、衝突のあとSASを入れたまま地面で静止するカプセル | 現在のRustエンジン |

v1とv2は、物理をJavaScript版のソルバーからRustエンジンへ移す前に記録した基準で、いまはRustエンジンで再生して照合します。記録に使ったソルバーはもうないので、この2つは凍結されており、記録し直すことはできません。初期状態として含まれる保存データは、当時の種別名（`orbital-foundry-flight`）と形式の版（1）のままです。保存データの読み込みがいまも以前の種別名と版1を受け付けるのは、この基準を再生するためです（`src/app-id.ts`、`src/flight-save.ts`）。

v3はRustエンジンで記録した基準です。機体どうしの衝突はRustエンジンにしかないので、v1・v2とは別の版になっています。

4件目の `capsule-tank-rest-after-impact` は、v2の `capsule-tank-impulse-ranking` と同じ初期状態・同じ操作列です（`tools/golden/scenarios-v3.mjs` がv2のファイルから定義を読みます）。v2ではこのケースの最後の電力を照合しなくなったので（下の「照合をやめた値」）、現在のエンジンでの結果をv3で固定しています。定義はv2のままなので、このケースでは機体どうしの衝突は無効です。

現在のファイルは、地面との接触を毎ステップ求め直し、ソルバーの原点を毎ステップ機体の位置に置くようにしたときに記録し直したものです。それまでの3件は、以前の記録との差が許容幅の中に収まっています（`orbit-bump-2ms` と `orbit-crash-30ms` は同じ値、`fuel-tank-impact-fragments-collide` は最大で許容幅の0.39倍）。

どのケースも、試験用の初期条件から始まる短い再生です。打ち上げから帰還までの通しの飛行を代替するものではありません。

### ファイルの内容

- `version`：基準の版（1〜3）
- `provenance`：記録したときの環境（下記）
- `tolerances`：比較の許容幅
- `cases`：ケースの配列。それぞれ `definition`（名前、時間刻み、ステップ数、比較のモード、初期状態の保存データ、操作列、記録するステップ）と `expected`（記録された結果）を持ちます。

`provenance` の項目：

| 項目 | 版 | 意味 |
|---|---|---|
| `revision` | 全部 | 記録したときのコミット |
| `node`、`platform`、`arch` | 全部 | 記録したNode.jsの版とOS、CPU |
| `recordedAt` | 全部 | 記録した日時（UTC） |
| `rapier` | v1、v2 | 記録に使ったnpmのRapierの版 |
| `runtimeJavaScriptSHA256` | v1、v2 | 記録したときの実行用JavaScript一式のハッシュ |
| `physics` | v3 | `rust-wasm` |
| `rapierRevision` | v3 | `engine/Cargo.toml` が固定しているRapierのリビジョン |
| `engineWasmSHA256` | v3 | 記録に使った `src/engine/orbital_engine.wasm` のSHA-256 |

`revision` は記録した時点のリポジトリの履歴でのハッシュです。現在の履歴に同じハッシュのコミットがあるとは限りません。

### 再生する

```sh
node --test tests/golden-replay.test.mjs   # 3つの版すべてと、比較そのものの試験
node tools/golden/run.mjs                  # v1をケースごとに再生して結果を表示
node tools/golden/run.mjs --v2
node tools/golden/run.mjs --v3
```

どちらも `dist/` を読み込むので、先に `npm run build` を実行します。`npm test` にも含まれます。`run.mjs` はケースごとに、許容幅に対する最大のずれの比（`maxToleranceRatio`）を表示します。

`tests/golden-replay.test.mjs` は再生に加えて、比較が甘くなっていないことも確かめます。操縦可否・部品構成・燃料の違いを検出すること、接触インパルスをすべて0と読んだ場合にv2が失敗すること、機体どうしの衝突を無効にした場合にv3の衝突の3件が失敗すること、照合をやめた値のほかは同じケースでも差を検出すること、などです。

### 比較の規則と許容幅

比較は `tools/golden/compare.mjs` が行います。許容幅は基準ファイルの `tolerances` に記録された値を使います。

| 量 | 許容幅 |
|---|---|
| 位置 | 0.05 m |
| 速度 | 0.02 m/s |
| 角速度 | 0.002 rad/s |
| 姿勢 | 0.002 rad（クォータニオンの符号の反転は同じ姿勢とみなす） |
| 時刻 | 0.0001 s（破損イベントの時刻は0.1 s） |
| 燃料 | 0.0001 ＋ 値の0.00001倍 |
| 電力 | 0.001 |
| 温度 | 0.1 K |
| アブレーター | 0.0001 |

- 上の表にない数値と、数値以外の値（部品構成、段、操縦可否、破損の原因と結果など）は完全一致を要求します。
- 非有限の値（NaN、無限大）が1つでもあれば失敗です。
- 凍結した基準のうち照合をやめた値は、下の「照合をやめた値」に従って扱います。
- モードが `impact` のケースでは、機体と破片の位置・速度・姿勢・角速度は記録するだけで、一致を要求しません。衝突後の破片の軌跡はわずかな差で大きく変わるためです。部品構成、状態、資源、破損イベントは比較します。

### 照合をやめた値

v1とv2は記録し直せません。そのため、記録された値がエンジンの不具合を含んでいて、その不具合を直した結果として値が変わった場合は、基準のファイルは書き換えずに、その値だけを照合の対象から外します。外す値は `tools/golden/retired.mjs` の一覧に、基準の版・ケース名・値の場所（`result.samples[3]…` の形）・理由を書きます。`tests/golden-replay.test.mjs` と `tools/golden/run.mjs` はどちらもこの一覧を読みます。

- 一覧にある値は、記録された値との差を見ません。ただし、再生した結果にその値が有限の数として存在しなければ失敗です。
- 同じケースのほかの値と、ほかのケースは、これまでどおりすべて照合します。
- 一覧の項目が基準のどのケースにも、またはケースのどの値にも当たらなければ失敗です。使われなくなった項目が一覧に残ることはありません。
- `run.mjs` は、値を外したケースの行に `retiredFields` としてその場所を表示します。

いま外している値は1つです。

| 版 | ケース | 値 | 記録された値 | 現在の値 | 許容幅 |
|---|---|---|---|---|---|
| v2 | `capsule-tank-impulse-ranking` | 4つ目の記録（2秒後）の、カプセルの電力（`result.samples[3].vessels[0].resources[0].charge`） | 990.82393 | 990.82551 | 0.001 |

このケースでは、タンクを失ったカプセルが約1秒後からSASを入れたまま地面の上で静止します。記録に使ったソルバーは、地面と機体が一緒に動くあいだ地面側の接触点を古い位置のまま使い続けていたので、静止した機体が細かく揺れ、SASがその揺れを打ち消すために電力を使っていました。記録された電力はその分だけ少なくなっています。現在のエンジンは接触を毎ステップ求め直すのでこの揺れがなく、電力の消費が0.0016少なくなります。このケースの部品構成、破損した部品とその原因、ほかの時刻の電力、温度などは引き続き照合します。直した後の結果は、v3の `capsule-tank-rest-after-impact` が固定します。

### 新しい基準を記録する

記録できるのはv3だけです。

```sh
node tools/golden/run.mjs --v3 --record
```

`--record` は次の条件を確かめます。

- `src/`、`engine/`、`tools/golden/` に未コミットの変更がないこと。記録はコミット済みのソースとコミット済みのWasmで決まるようにするためです。
- `engine/Cargo.toml` がRapierをgitのリビジョンで固定していること。
- 出力先のファイルがまだないこと。既存の基準を上書きしません。記録し直すときは、先に古いファイルを削除します。

そのうえで `dist/` をビルドし直し、`tools/golden/scenarios-v3.mjs` のケースを再生して書き出します。機体と部品のIDは記録のたびに新しく振られるので、初期状態の保存データのIDは記録ごとに変わります。v1・v2に `--record` を付けるとエラーになります。

基準を記録し直すのは、物理の結果が意図して変わるときだけです。意図しない差が出たときに、基準を記録し直したり許容幅を広げたりして試験を通してはいけません。結果を変える変更では、変更の理由と、その変更を直接確かめる別の試験を用意したうえで、記録し直した基準を同じコミットに含めます。
